# Troubleshooting

- **The setup code is not in the log, or is refused:** until a code is used, every start prints a new one and only the latest works. Run `docker compose restart mailsift`, then `docker compose logs mailsift`. Once an administrator password is set, no code is printed; sign in with the password.
- **The administrator password is forgotten:** `docker compose exec mailsift node dist/src/main.js --reset-admin` clears it and every browser session and prints a new one-time code. Open the page and choose a new password; mailboxes and settings are not touched. See [Deployment](deployment.md#signing-in).
- **mailsift does not start, and the log says the stored settings cannot be read:** the key in the `mailsift-secrets` volume is missing, or is not the key the settings were written with. Restore it from the backup of that volume. To start over instead, remove both volumes with `docker compose down -v`. See [Deployment](deployment.md#backups-and-the-encryption-key).
- **A page says "Open mailsift over HTTPS or from localhost", or a client gets `https_required` (403):** mailsift was reached at an address that is neither localhost nor HTTPS, where a password or token would cross the network in clear. Use an SSH tunnel (`ssh -N -L 8410:127.0.0.1:8410 you@your-server`) and `http://127.0.0.1:8410/`, or an HTTPS reverse proxy that sets `X-Forwarded-Proto`. See [Deployment](deployment.md#reaching-it-from-another-computer).
- **MCP answers `503` with `setup_required`:** setup is not finished. Until **Start mailsift** is pressed in the last setup step, no mailbox is checked and MCP answers only this.
- **After a save, Settings says "mailsift has not come back yet":** the service did not start again. `docker compose logs mailsift` says why.
- **After a save, the page says to restart mailsift by hand:** it was started without its supervisor, as `node dist/src/main.js`. Start it with `npm start` or `node dist/src/server.js` (the image and the systemd unit already do), and saved settings are applied by themselves. See [Deployment](deployment.md#how-saved-settings-are-applied).
- **`docker compose up` cannot pull the image:** the tag in the compose file's `image:` line must name a published release, written without the leading `v` (`0.2.0`, not `v0.2.0`), or be `latest`; the Releases page lists them.
- **Nothing was notified:** call MCP `health` first. Its `delivery` block reports the push and digest thresholds, the spam boost, and whether self-forwards are suppressed, which usually explains the decision without further digging. `recovery_status` then shows folder UID progress and any notification still queued for retry.
- **No digest arrives:** the digest is sent to the Feishu bot and the webhook. With neither set under Settings → Notifications, mail is still triaged and shown in the web view, but no digest is sent. See [Configuration](configuration.md#daily-digest).
- **A mailbox stopped being checked:** the web view names it under the status line, and tapping the line shows the kind of failure, what usually fixes it, and a link to its settings; see [Web view](web-view.md#mailboxes-that-cannot-be-read).
- **The Google sign-in ends on a page that does not load (`http://localhost:8765/…`):** that is expected when the page is reached over HTTPS. Copy the full address from the address bar into the **Finish signing in** dialog. A sign-in is good for 15 minutes; after that, press **Sign in** again. The same goes for Microsoft.
- **A Gmail mailbox needs signing in again every 7 days:** the OAuth consent screen is still in Testing. Publish it in Google Cloud Console. See [Deployment](deployment.md#gmail-and-outlook-sign-in).
- **Outlook refuses the sign-in:** IMAP is off in Outlook's own settings by default. Turn it on, then sign in again under Settings → Mailboxes.
- **Repeated notifications:** messages are deduplicated by mailbox plus Message-ID. Mailboxes that forward to each other are covered by **Ignore copies forwarded between your own mailboxes** ([Configuration](configuration.md#mailboxes-and-folders)). `--recover` is for interrupted, undecided records.
- **Delivery failures:** a push that fails with a network error, a timeout, or HTTP 408/429/5xx is retried and then waits in the durable outbox with exponential backoff; `recovery_status` shows the next attempt time. See [Configuration](configuration.md#delivery-retries).
- **Outbox backlog:** only real failures wait there. An output that declines a message under its own threshold, such as **Feishu receives**, settles it immediately and the digest carries it, so a pending count in MCP `health` always means something is genuinely undelivered.
- **The digest arrives at the wrong hour:** the digest hour is read in the server's time zone, Settings → Checking and digest → **Time zone**; see [Configuration](configuration.md#daily-digest).
- **QQ scans many messages:** some QQ IMAP endpoints ignore `SINCE`; the local UID cursor still preserves correctness.
- **Searching a QQ mailbox finds only subjects and senders:** QQ's IMAP search answers some searches with the wrong messages and ignores Chinese on some accounts, so "Search the mailbox" (and MCP `search_mailbox`) does not ask it. It reads the envelopes of the newest 2,000 messages of each folder searched and compares only their subject and sender, and says so above the results (`limited` through MCP). The same happens on any server that refuses a search, or finds nothing for text outside ASCII. Mail older than those 2,000, or a word only in a message's text, is not found that way: open the folder and page back, or search in the provider's own client. Stored mail is searched by the ordinary search field, which is not affected.
- **Messages marked read:** polling and opening a message in the web view use read-only mailbox locks and `BODY.PEEK[]`, so neither marks anything read. A message is marked read only when you mark it done in the web view, signed in with the administrator password or the write token, or through MCP `manage_mail` or `mark_handled`.
- **The web view says the session can only read:** it was signed in with the MCP read token. Open `/signin` and sign in with the administrator password. See [Web view](web-view.md#signing-in-and-what-a-session-may-do).
- **A reply cannot be sent:** the composer says why. "Not set up to send" is a mailbox on a custom host with no **SMTP server** under its Server and sending. "Sending is switched off on the server" means Settings → Web mail → **Allow sending from the web view and MCP** is off, or Settings → Notifications → **Dry run** is on. "Authorized for reading only" is an Outlook mailbox signed in before sending was allowed; press **Sign in again** on it under Settings → Mailboxes and allow sending on Microsoft's consent screen. A refused sign-in for a password mailbox usually means the provider wants SMTP switched on in its own settings (QQ and 163 do), or a separate app password. See [Configuration](configuration.md#sending-mail).
- **No "Verified sender" line under a sender:** the reader shows a provider's verdict only when it can tell the provider wrote it. Outside Gmail, Outlook, Yahoo, iCloud, Fastmail and QQ, enter the mailbox's **Authentication-Results server ID** under its Server and sending; see [Web view](web-view.md#reading-a-message).
- **Notifications never arrive:** they need HTTPS or a localhost address, and on iPhone and iPad the app installed to the Home Screen. Use the test button in the panel under the bell. If the test is sent but nothing shows on an Apple device, set Settings → Notifications → More options → **Contact for push services** to a real `mailto:` address. A device's notifications are tied to the token its browser holds (the write token, for a browser signed in with the administrator password), so after a new one is generated in Settings → Access, each device has to turn them on again.
- **The log fills with `transient IMAP connection failure`, `Login failed` or `User is authenticated but not connected` for a mailbox that worked a minute ago:** the provider is stalling or refusing sign-ins, which Outlook in particular does when it is in trouble or sees several sign-ins at once. Nothing is wrong with the token. Each line says who was connecting (`for the poll`, `for listening on INBOX`); mailsift spaces its sign-ins to one mailbox, gives each attempt thirty seconds, tries a refused token once more, and the next poll picks up whatever was missed. An alert is sent only after **Alert after failed checks in a row** polls have failed, and a recovery notice follows.
- **Opening a message says the mailbox is slow:** the message is read from the provider at that moment, so a provider that is dropping connections shows up here first. The log names it (`transient IMAP connection failure`, `User is authenticated but not connected`). The page tries further connections beside a stalled one and, within about fifteen seconds, says the provider is not answering and offers a retry; the list, the summaries and everything triage stored stay readable meanwhile.
- **The page is a minute behind and shows no live dot:** the proxy in front is buffering or cutting `/api/events`; see [Behind a reverse proxy](web-view.md#behind-a-reverse-proxy).
- **LLM privacy:** Settings → Privacy and retention → **Judge codes and sign-in links locally** keeps verification-code messages away from the model, and **Redact identifiers before the model sees them** redacts common direct identifiers before fields are sent; both are on by default. Leave the API key empty for the local keyword fallback, or use a self-hosted endpoint. See [Triage](triage.md).
- **OAuth expiry:** access tokens refresh automatically. After access is revoked or the account's password changes, sign in again from the mailbox's entry under Settings → Mailboxes.
