# MCP

mailsift includes an MCP server, so an AI assistant can see what needs you, list, search and read your triaged mail, reach the rest of the mailbox live, preview the digest, look at attachments and at what your provider said about a sender, and check whether mailsift is healthy. With a second, write token it is given what the web view's owner has: it can mark mail done, file it, bin it, and send mail.

An agent that supports skills can load [`.agents/skills/mailsift/SKILL.md`](../.agents/skills/mailsift/SKILL.md), which says how these tools are meant to be used and where the limits are.

## Connecting

The endpoint is `/mcp` on the page's own address: `http://127.0.0.1:8410/mcp` on the server or through an SSH tunnel, or `https://mail.example.com/mcp` behind an HTTPS reverse proxy (see [Deployment](deployment.md#reaching-it-from-another-computer)). It uses stateless Streamable HTTP, with a token as the bearer credential: `Authorization: Bearer <token>`. Like the page, it accepts a token only over HTTPS or at a localhost address, and answers anything else with `403` and `https_required`. Until setup is finished it answers `503` (`setup_required`).

Two random tokens are created at first start, a read token and a write token, each starting `ms_`. Neither is ever displayed. To give one to a client, open Settings → Access → MCP and press **Generate new** beside it: the new token is shown once, with a Copy button, and the old one stops working when mailsift restarts to use the new one, a moment later. The read token reads triage results and mail; the write token also acts on mail and sends it (see [Write tools and the write token](#write-tools-and-the-write-token)). The two are always different. Neither can change settings, which need the administrator password, and the one-time setup code is not an MCP credential either.

Settings → Access → More options → **MCP requests per client per minute** (`MCP_RATE_LIMIT_PER_MINUTE`, default `120`) applies per client. The web view on the same port has a separate request budget, so a busy MCP client does not lock the owner's browser out.

A local stdio client can start the MCP server inside the container instead:

```bash
docker compose exec -i mailsift node dist/src/mcp.js
```

From a source checkout the command is `node dist/src/mcp.js`, or `npm run mcp`. It reads the same stored settings and runs as the service's own user, so it needs no token and has the write tools: give it only to a client you would hand your mailbox to.

## Tools and resources

| Tool | What it does |
| --- | --- |
| `needs_you` | The queue the web view opens on: mail judged to matter that nobody has dealt with yet. A row with `withheld: true` was due a notification that was not sent because you had already answered it from another client or marked it done; it is not quiet digest mail. Optionally also what was dealt with in the last seven days (`DONE_LIST_DAYS`; the most recent 50, with `recentlyDoneCount` for all), and what is put off until later. Start here for "what needs me". |
| `list_mail` | Recently processed mail (24 hours by default), filtered by level, exact category, mailbox, spam only or pushed only. |
| `list_threads` | Recent conversations, grouped by their References/In-Reply-To root, each with how many of your own messages it holds in the window (`sentCount`) and whether the latest word is yours (`lastWordYours`). |
| `search_mail` | Keyword search, exactly as typed (`%` and `_` are ordinary characters), over subject, sender, category, summary, reason, the stored body preview and the names and types of attachments, or for a whole Message-ID; `account` keeps one mailbox's mail. |
| `get_mail` | The stored triage record for one Message-ID, with a bounded body preview. |
| `mail_summary` | Processed and pushed totals for a time window, spam and spam rescues included. |
| `list_digest` | The messages waiting for the next daily digest. |
| `list_accounts` | The monitored mailboxes, their providers and the folders being watched; with the write credential, each mailbox's signature. |
| `list_folders` | One mailbox's IMAP folders, what each is for, and how many messages each holds and how many are unread where the server says so cheaply. |
| `browse_folder` | One folder of a mailbox, live, newest first, a page at a time: any folder, and older mail than mailsift keeps. Each message has a live handle. |
| `search_mailbox` | A search the mailbox's own server runs (Gmail in its own syntax), live, for mail mailsift never stored. Says when it could only read the subject and sender of recent mail. |
| `find_contacts` | Addresses for a name or part of one, as the web view's composer suggests them: those you have written to first, then people who wrote to you. |
| `read_message` | One message as the web view shows it, read live: its text with the quoted history apart, who it is from and to, the provider's verdict on the sender, its flags and folder. Takes a stored Message-ID or a live handle. |
| `prepare_reply` | What an answer to a message would start from: recipients, subject, thread references, the original quoted. Sends nothing. |
| `prepare_forward` | What a forward of a message would start from: its subject, the forwarded block, and the original's attachments by part id. Sends nothing. |
| `list_attachments` | A message's attachments, each with a resource URI to fetch the file. |
| `scan_attachment` | A bounded local check of one attachment. |
| `inspect_mail_safety` | Spam and safety clues for one message, with what the mailbox's provider reported about the sender. |
| `health` | Last poll, mailbox failures, LLM status and queues. Start here when a notification is missing. |
| `recovery_status` | Mailbox health timelines, folder UID progress, dead letters, and notifications queued for retry. |
| `list_dead_letters` | Messages skipped because they were oversized or could not be parsed. |
| `observability` | Totals for processing, delivery, dead letters, feedback and mailbox actions, plus access audit by tool. |
| `list_audit` | Recent tool and resource calls and audited mailbox actions. |
| `feedback_rules` | Sender rules inferred from feedback. |
| `manage_mail` | Write: mark read or unread, star or unstar, archive, bring back to the inbox, bin, move, spam or not spam; one message or up to 100. A message already where the action would put it is left there and answered as done, with `already: true`. |
| `mark_handled` | Write: say a message is dealt with, which takes it out of `needs_you`, or put it back; one or up to 100. |
| `snooze` | Write: put a message out of `needs_you` until a time, when it comes back and the owner's devices are reminded; bring it back now; or cancel the reminder. |
| `send_mail` | Write: answer a stored message, forward one with its attachments, or send a new one, from a monitored mailbox. |
| `set_signature` | Write: set or remove a mailbox's signature, the plain text the page and `send_mail` put under a letter from it. |
| `record_feedback` | Write: label a message `false_positive`, `missed`, `handled`, `correct`, `spam` or `not_spam`. |
| `retry_dead_letter` | Write: rewind one folder cursor so the next poll retries a dead letter. |

### Resources

| Resource | What it reads |
| --- | --- |
| `mailsift://search-syntax` | Every filter the tools accept, the category and importance vocabularies, and what the store does not hold. Rendered from the constants the triage code uses, so it cannot describe a vocabulary that no longer exists. |
| `mailsift://mail/{messageId}` | One stored judgement as a markdown page: headers, how it was judged and why, the bounded body preview, the attachment list. |
| `mailsift://thread/{threadKey}` | A conversation as one markdown page, oldest first: its newest 50 messages, your own among them and marked as yours, with a line saying how many older ones are left out. Thread keys come from `list_threads`. |
| `mailsift://imap/{account}/{messageId}` | A bounded normalized body with its headers, as a JSON object, fetched from the mailbox on demand. |
| `mailsift://imap/{account}/{messageId}/attachment/{partId}` | One attachment, fetched on demand. |

The first three are markdown because a model reads them: the headings say what each field means, which a JSON object has to be told. The same records are still JSON from `get_mail` and `list_threads`, which is what an application should parse. Nothing fetched live is persisted. The webhook's [signal event](signal-event-v1.md) carries the `mailsift://imap/...` form as its reference.

No answer here carries a verification code. Mail with a code or a sign-in link is judged locally and never sent to the model, and its record's subject, summary and preview say only what arrived. The record keeps the code for the web view's code lane, where the owner asked to see it, and every tool and resource leaves it out: an MCP client is a model whose answers can go anywhere, holding a token that may be shared. `read_message` and `mailsift://imap/...` read the message itself from the mailbox, as the owner could, code included.

### Your own mail

The poll reads each mailbox's Sent folder, and what `send_mail` and the web view send is stored as it leaves (see [The conversation, and your own mail](web-view.md#the-conversation-and-your-own-mail)). It is stored locally like the snippets of the mail you receive, used for the conversation only, and never judged or sent to the model. Three things read it:

- The thread resource lists your messages among the others, the newest 50 of the conversation (`Older messages not shown: N` says what was left out), each marked "From the owner", with whom it went to (To, Cc and Bcc), its date, its subject when it differs, the names of its files, and the text you wrote without the quoted history below it, at most 8,000 characters. A conversation that holds only your own messages so far can be read there too.
- `list_threads` stays the mail you received in the window, and says of each thread how many of your messages it holds in that window (`sentCount`) and whether yours is the latest word (`lastWordYours`). A copy of one of your own messages that came back into the mailbox (a mailing list's, a Bcc to yourself) is counted as yours, once, here and in the thread page.
- `find_contacts` (`query`, `limit` up to 20, default 8) turns "write to Alice" into an address. It ranks the addresses you have written to, in To, Cc or Bcc, by how often and how lately, then people who wrote to you and look like people: not spam, not newsletters, notices, codes or no-reply and other role addresses, not your own mailboxes. A name matches from the start of any of its words, an address from the start of its local part, of a word of it or of its domain, in either case, and a Chinese, Japanese or Korean name anywhere in it. Each result has one name, the most recent one seen with the address, and `source`: `sent` (written to) or `received` (only ever wrote). It needs only the read credential. Names were written by whoever sent the mail; ask the user when more than one address fits.

`needs_you`, `list_mail`, `search_mail`, `get_mail` and the digest are received mail only. A reply found in Sent takes the message it answers out of `needs_you`, as answering it through `send_mail` does; see [What needs you](web-view.md#what-needs-you) for the rule. Turning off Settings → Privacy and retention → **Read Sent folders into conversations** stops reading and storing it.

`list_folders` takes the exact account address returned by `list_accounts` and lists its decoded IMAP folder paths, each with its `name` and `parent`, its `role` (`inbox`, `archive`, `all`, `sent`, `drafts`, `junk`, `trash`, `starred`, `important`, or null for a folder of the owner's own), hierarchy delimiter, flags, special-use marker and selectability, the inbox and the other folders every mailbox has first. `messages` and `unseen` are how many messages a folder holds and how many are unread, where the server says so cheaply: in the folder list itself (`LIST-STATUS`), or else by `STATUS` one folder at a time for a few seconds, the rest without them. It opens no folder and changes no mail. It is the list the web view's folder panel shows.

## The rest of the mailbox, live

The tools above are what mailsift fetched and judged: the monitored folders, within `STATE_RETENTION_DAYS`. `browse_folder` and `search_mailbox` reach the rest, live from IMAP: any folder, older mail, the archive, the Sent folder. They read envelopes and flags only, never a body, store nothing, and nothing they list is judged, sent to mailsift's model or put in `needs_you`. They need only the read credential, and are what the web view's folders and its "Search the mailbox" show.

- `browse_folder` (`account`, `folder` as `list_folders` gives it, `limit` up to 100, default 50) lists a folder newest first. `next` is passed back as `before` for the next page; it is tied to the folder's UIDVALIDITY, and a folder rebuilt in between is refused with `NOT_FOUND` (`liveCursor`), to be listed again from the top.
- `search_mailbox` (`account`, `query`, optional `folder`, `before`, `limit`) runs the mailbox's own search, newest first, on a connection of its own, so the mailbox's other calls do not wait behind it. A mailbox has at most two such connections (providers limit an account's sessions); more searches at once wait their turn. A search still running after 25 seconds is stopped, its connection closed, and the call fails with `MAILBOX_UNAVAILABLE` and the hint to narrow the search to one folder; a provider that cannot be reached at all is said as that. Paging through the inbox and the archive together gives each hit once. Without `folder` it searches the inbox and the archive; on Gmail, All Mail alone, in Gmail's own syntax (`from:`, `has:attachment`, `older_than:1y`). Elsewhere the subject, the sender and the text are searched, in UTF-8 where the query needs it. QQ's IMAP search cannot be trusted (it answers some searches with the wrong messages and ignores Chinese on some accounts), so on QQ, and on any server that refuses a search or finds nothing for text outside ASCII, the newest 2,000 messages of each folder searched are read envelope by envelope and only their subject and sender compared. The answer then has `limited` (`reason`: `provider`, `refused` or `unicode`; `scanned`: how many were read): it is not a full search, and an assistant must say so.

Each message they list has `from`, `to`, `subject`, `date`, `size`, `flags` (`seen`, `flagged`, `answered`), `attachments` (whether it carries files) and a `handle`, a string that starts `live:` and names the message by its mailbox, folder, the folder's UIDVALIDITY, its UID and its Message-ID, signed by this server with a key kept in the state database. A message mailsift stored also has `key` (its `dedupKey`) and `stored`: how it was judged and whether it was dealt with or put off. A listed message is the stored record only where the record says it is: the same mailbox and folder and, when the record has its UID, the same UID in the same UIDVALIDITY; for a record with no UID known, or whose remembered UID no longer holds its message, only its first message in that folder from its sender (the one the poller stored first, and the one its key finds), which the listing asks the mailbox about as it lists, in one search per page; the listing then keeps its UID, so the match holds after a restart and in another process. A later copy from the same sender has no `key`, and neither does any copy when the mailbox cannot say which is first (QQ's search cannot, so it is not asked there). `manage_mail` on such a message by its handle then checks, as it acts, whether the record's own lookup finds this very message, and if so keeps the record's books. A message without a Message-ID is matched by its place alone. A Message-ID too long to carry in a handle is carried as its SHA-256 digest; such a handle works like any other. Another message with the same Message-ID (a copy in Sent or another folder, or a look-alike a sender wrote with a borrowed Message-ID) has no `key`, and nothing done with its handle touches the record.

A Message-ID or key that names a stored record of the mailbox asked about is looked for as that record is, by every tool and resource that reads the mailbox (`read_message`, `list_attachments`, `inspect_mail_safety`, `scan_attachment`, the `mailsift://imap/...` resources): where mailsift last saw it, and anywhere else only from the record's sender, so a look-alike that borrowed its Message-ID is answered as not found. An id nothing is stored about is searched for as it is. A handle can be given wherever a tool takes a `messageId`: `get_mail`, `read_message`, `prepare_reply`, `prepare_forward`, `list_attachments`, `inspect_mail_safety`, `scan_attachment`, the `mailsift://imap/...` resources, `manage_mail`, and `send_mail` as `replyTo` or `forward`. `get_mail` answers a handle with the record of that very message, or `found: false` for a message mailsift never stored. Use the item's `handle`, never its `messageId`, to act on a listed message: the Message-ID is the sender's text and may name another. The message is then read and acted on exactly where the handle says. Each time, the server checks that the mailbox is configured, the folder exists and has not been rebuilt, and that the UID still carries that Message-ID (under the writable lock, for an action); when one of these no longer holds the call fails with `NOT_FOUND` and a hint to list the folder again, and nothing is looked for elsewhere. A handle that is not one this server made, or whose signature does not match, is `INVALID_ARGUMENT`. After a move, `manage_mail` answers with the message's new `handle` where the server said where it landed. A message named by a handle that mailsift stored is the stored record for everything else: archiving or binning it counts it as dealt with, answering it takes it out of `needs_you`. `mark_handled`, `snooze` and `record_feedback` take a handle only for such a message, and refuse one for a message mailsift never stored with `ACTION_REFUSED`: it has no place in the queue and no judgement to correct. A sender can write a Message-ID that looks like a handle: a string that starts `live:` only ever names a live message, and one that is also a stored record's Message-ID or key is refused with `INVALID_ARGUMENT`, to be named by the record's `dedupKey` instead. Without the server's key a sender cannot sign one, so a Message-ID can never pass for another message's handle. Reading a message by its handle never changes where its record says it is.

A message mailsift never stored that `manage_mail` moves (`move`, `archive`, `trash`, `inbox`, `spam`, `not_spam`) is written down as filed by the owner where it lands, so that when it lands in a monitored folder the poll does not take it for new mail: it is not judged, notified, queued or put in a digest.

The audit records which mailbox and folder were browsed or searched, never what was searched for.

## Prompts

Prompts are workflows, not questions. Each one fixes an order of tool calls that works and says when to stop, because a model asked something broad usually starts with a search, and a search cannot answer a question about mail that was never delivered.

| Prompt | Arguments | What it does |
| --- | --- | --- |
| `catch_up` | `hours`, optional `focus` | Reports what arrived and what needs action, starting from `needs_you` and reading `mail_summary`, `list_mail` and the pending digest rather than searching. It changes nothing. |
| `why_not_notified` | `about` | Diagnoses a missing notification in order: was the mailbox read, was it judged above the threshold, was it delivered. Starts at `health`, which answers most cases on its own. |
| `review_triage` | `hours` | Goes through recent judgements and records feedback on the wrong ones. Asks before recording anything, because two records for one sender become a standing rule. Offered only to a caller holding the write token. |

## Errors

Every failure carries a `code` a caller can branch on, a message, and a `hint` naming the next move. Tools answer with `isError` and the body as JSON, arguments the schema refuses included (and such a call is audited as a failed call of that tool); resource reads carry the same body in the JSON-RPC error's `data`.

| Code | Means |
| --- | --- |
| `NOT_FOUND` | The id is unknown to mailsift, or the message has no attachment with that part id. |
| `ACCOUNT_UNKNOWN` | That address is not one of the monitored mailboxes. |
| `INVALID_ARGUMENT` | An argument does not match the schema (named in the message), a `cursor` this server did not give, or a resource URI is malformed. |
| `MAILBOX_UNAVAILABLE` | The mailbox itself could not be read just now. Stored records stay available. |
| `ATTACHMENT_UNSUPPORTED` | Skipped by the size or type limit: a file over `MCP_ATTACHMENT_MAX_BYTES` is not handed out. From `send_mail`, a forward whose attachments come to more than one message may carry (`send_too_large`): nothing was sent. |
| `ACTION_REFUSED` | The mailbox or the mail server refused: a folder that does not exist, a recipient the server would not take, too many messages in a minute. |
| `WRITE_DISABLED` | No write credential is configured. |
| `SERVER_MISCONFIGURED` | mailsift cannot read its own settings. This needs a person, not another call. |
| `PROVIDER_ERROR` | Anything else. The underlying message is never passed through, because it can carry a credential. `send_mail` answers with this code and `send_timeout` in its message when the mail server did not confirm a message: it may have left, so look in Sent before sending again. |

A Message-ID that was never seen is not an error: `get_mail` answers `found: false`, because absence is a result.

## Write tools and the write token

`manage_mail`, `mark_handled`, `snooze`, `send_mail`, `set_signature`, `record_feedback`, and `retry_dead_letter` are write tools. They need the write token; a read token cannot change mailbox contents, send mail or change future triage policy.

**The write token is the owner's key.** A caller that presents it is given what a browser signed in with it has in the [web view](web-view.md#signing-in-and-what-a-session-may-do), and the tools run the page's own code, so the two cannot differ: the same checks, the same limits (ten messages a minute per client), the same audit. That includes the two things that act for you in the world, binning a message and sending one. The page can do one thing more, attach a file from the device it runs on (see what stays with the page, below). An MCP client is a model, and the mail it reads is written by strangers who can address it directly, so give this token only to a client you would hand your mailbox to, and prefer one that asks before it sends. The server's instructions, each tool's description and the [skill](../.agents/skills/mailsift/SKILL.md) all tell a model to act only on your request and never on a message's; that is guidance, not a lock. Turning off Settings → Web mail → **Allow sending from the web view and MCP** switches sending off for the page and for MCP alike.

`manage_mail` supports `mark_read`, `mark_unread`, `star`, `unstar`, `archive`, `inbox`, `trash`, `move`, `spam` and `not_spam`. `archive` files a message in the mailbox's own archive folder (All Mail on Gmail; refused where there is none); `inbox` brings one back from spam, the archive or the bin; `trash` moves it to the mailbox's bin, which the provider empties on its own schedule; `move` takes a folder path from `list_folders`. `spam` moves a message into the mailbox's spam folder and records `spam` feedback for it; `not_spam` moves a message that is in the spam folder to the inbox and records `not_spam` (it is refused for a message anywhere else); a mailbox with no spam folder is refused with `ACTION_REFUSED` rather than given one. Archiving, binning and spam count the message as dealt with, and so does a `move` into the bin or a folder inside it. Every operation looks the message up again in the mailbox, starting where mailsift last saw it, and checks its Message-ID inside a writable IMAP lock before changing anything; then it records an audit row. Found anywhere but where mailsift last saw it, a message is the stored one only when it is from the record's sender: once the real message is gone, a look-alike with its Message-ID is answered `NOT_FOUND`, not read, answered or acted on in its name, and the record is never moved to it. After a move the stored record follows the message, so the web view and the next call look where it now is.

`mark_handled` is the ring in the web view: it takes a message out of the queue, or with `handled: false` puts it back. Marking one done also marks it read in its mailbox, in the background, and that is audited too; a mailbox that cannot be reached does not undo the mark.

`manage_mail`, `mark_handled` and `snooze` take `messageIds` (up to 100) instead of `messageId` to act on several at once, as the web view's bar does: one request, each mailbox reached eight messages at a time so other calls are not held up, each message checked as it would be alone and audited as it would be alone (`mark_handled` and `snooze` write one audit row for every id asked about, with what came of it: done, skipped or refused). The answer has `done`, `skipped`, `failed` and `pending` counts and a result per id: `status` `done`, `skipped` (the action does not apply: `notStored` for done or snooze on a message mailsift never stored, `unchanged` for one already so, `alreadyDone` for a `snooze` of one marked done, which stays done, `notApplicable` for not_spam outside the spam folder; a message already in the destination is left there and counted `done`), `failed` with a `code` and why (`NOT_FOUND` for an id mailsift does not know, `liveStale` for a handle that no longer fits), or `pending` when the mailbox had not answered for it by the time the call returned; a pending one is recorded when the mailbox answers, and listing again shows where it is. One id that fails does not fail the others or the call. `newlyNeverImportant` lists senders whose mail a `spam` call just made low priority.

`snooze` is the web view's "Remind me" ([Later](web-view.md#later)): "not now, remind me at nine on Monday". `until` is an ISO 8601 time with its offset and seconds, written in the owner's own time zone (for example `2026-11-16T09:00:00+08:00`), still to come and at most a year ahead. The tool's description names the server's time zone (Settings → Checking and digest → Time zone, Asia/Shanghai in the published image until it is changed) so an assistant has a zone to start from, and the answer adds `snoozedUntilLocal`, the same time on the server's clock. A time without an offset is refused by the argument schema, and one in the past or further off with `INVALID_ARGUMENT` (`snoozePast`, `snoozeFar`). The message leaves `needs_you` at once. From that minute it is back in it for 30 days, whatever it was judged, since the owner asked to be reminded, and every device with the web view's notifications on is told ("Reminder: <sender>"). Putting off a message that was marked done puts it back, since a reminder is for what is not done. `until: "now"` brings it back at once, as the page's "Back now" does: its reminder counts as having come, so it is in `needs_you` whatever it was judged and however long ago it arrived, and no device is notified, since the owner is the one asking. `until: null` cancels the reminder instead and leaves the message to its judgement: it is in `needs_you` only if it was judged to matter (critical or notified) and arrived within the last 30 days, and otherwise only in the list (`list_mail` with `hours`, or `search_mail`, reaches older mail). The answer's `inNeedsYou` says where it is. A message put off is not notified as new mail before its time, on any output, even when it is judged again meanwhile; a notification that was waiting for a retry, or that a late verdict calls for, goes out on Feishu or the webhook at the time chosen (sooner if the time is moved sooner, at once if the reminder is cancelled, never after "now"), and one for a message marked done is dropped. `recovery_status` marks such a waiting notification with `heldUntil`, and the health counts leave it out of what is waiting to be delivered. It changes nothing in the mailbox. `needs_you` with `includeSnoozed: true` adds `snoozed`, what is put off and still to come, soonest first, each with its `snoozedUntil` (the first 50; `snoozedCount` says how many in all); every record carries `snoozedUntil` (null when no reminder was asked for), and in `needs_you` a past one says the message is there because a reminder brought it back.

`send_mail` is the composer. With `replyTo` (a stored Message-ID) the answer leaves from the mailbox that received the original and continues its thread. Where `to` is left out it goes to whoever the original asks answers to, or to its sender when the original asks for answers only at your own address. Where the message names no sender and no reply address, or is from your own address (which a sender can forge, and where the page's composer would continue it to everyone it went to), `send_mail` refuses until `to` is given, and with `to` given and `replyAll` the others are copied. Where `cc` is left out, `replyAll: true` puts the other recipients in copy (never your own addresses, and nobody twice). The subject is "Re:" the original's, and the original is quoted below the text unless `quote: false`. If the original can no longer be read from its mailbox, an answer still goes when `to` and `quote: false` are given (and `cc` too with `replyAll`, since who else it went to cannot be read either), under "Re:" the subject mailsift stored; for a message it never stored, named by a live handle, `subject` is needed as well, since nothing else says what it was about. With `account` instead of `replyTo` it sends a new message from that mailbox. Text is plain text, and the mailbox's signature goes under it (after the standard `-- ` line, above any quote or forwarded message) unless `signature: false`. Afterwards, as in the page, a copy is filed in Sent where the provider does not file one itself (`savedCopy` says whether one is there), the original is marked answered and counted as dealt with, and the audit has a row saying that a message left, from where and when, without its recipients or its text. The letter itself is stored for its conversation, as in the page (see [Your own mail](#your-own-mail)). A `note` in the result says something about where it went: an answer addressed for the caller to a Reply-To on another domain than the sender's, or with no sender address to compare it with (`prepare_reply` shows the same as `replyToElsewhere`, and where `to` came from as `addressedTo`), or an original that could not be quoted.

With `forward` (a stored Message-ID) and `to`, which a forward always needs, `send_mail` passes the message on: the subject is "Fwd:" the original's unless one is given, and under the text and the signature comes the forwarded block `prepare_forward` shows (who it was from, when, its subject, who it went to, then its text). A forward starts a conversation of its own, so it carries no `In-Reply-To` or `References`, and the original is counted as dealt with but not marked answered, unless every recipient (`to`, `cc` and `bcc`) is one of your own mailboxes: a message forwarded from home to work, to deal with it there, stays in `needs_you`, since the copy that arrives at work is ruled a forwarded copy and not put before you again. `originalHandled` in the result says which, and the page follows the same answer. It leaves from the mailbox that received the original unless `from` (an address from `list_accounts`) names another of your mailboxes, as the page's From picker does, and then it carries that mailbox's signature; `account` only picks the copy when one message is stored for more than one mailbox. `text` may be empty for a forward, as in the page, and the letter then starts with the signature or the forwarded block; anything else needs words of its own. `includeAttachments` sends the original's attachments with it: `true` (the default) for what the page sends by default, every file but the pictures of the original's body; a list of part ids from `prepare_forward` for exactly those, pictures included when named; `false` or `[]` for none. A picture of the body (`inline: true` in `prepare_forward`) is an image sent inline whose Content-ID the original's markup shows: a logo, an icon, a portrait in a signature, which a plain-text forward would otherwise carry by the dozen as files nobody chose. Anything else sent inline is a file like the rest; Apple Mail sends a PDF or a photo that way. A part that holds other parts rather than being one file (a Mac file sent as `multipart/appledouble`) cannot be forwarded: `prepare_forward` lists it under `notForwardable`, and naming it is refused. The server reads each file from the mailbox as it sends, holds the whole letter to `SMTP_ATTACHMENT_MAX_BYTES` (20 MiB by default) and twenty files, and sends nothing if one of them cannot be read: `NOT_FOUND` or `MAILBOX_UNAVAILABLE` with `forward_attachment_unavailable` naming the file. Where the original cannot be read for its files when the forward is sent, nothing is sent either and no file is named: `forward_original_gone` (`NOT_FOUND`) when it was moved or deleted in its mailbox or no longer has that file, so find it again and forward it from there, and `forward_original_unavailable` (`MAILBOX_UNAVAILABLE`) when its mailbox did not list its attachments, so try again. Where the original's attachments cannot be listed at all, a forward that asked for any of them is refused rather than sent with fewer, as the page asks before it sends one without them. Each file goes as the sender attached it, byte for byte, and a text file keeps the character set it was labelled with. This is the only way a file leaves through MCP: by reference to a stored message's own attachments. Nothing can be uploaded, and the result names the files that went.

`set_signature` sets the signature of one mailbox (`account` and `text`, plain text of at most 2,000 characters; empty text removes it). It is the one the page's composer shows under a letter from that mailbox and lets the owner edit, so a change made here is a change there. Only that it changed, and for which mailbox, is audited, never what it says. `list_accounts`, `prepare_reply` and `prepare_forward` show signatures only to a caller holding the write credential, as the page shows them only to a session that may send.

One letter is sent once. A letter's name is what the caller called it (`id`, optional) bound to what it says and who it goes to, as the page names its own, so the same request repeated within fifteen minutes is answered with `repeated: true`, a `notice`, and the same account of the first attempt (mailbox, recipients, any `note`) instead of a second copy; a name reused for a different letter does not answer for the first. A repeat that arrives while the first attempt is still running waits for it as long as that attempt may take (a forward's reading of its files included, and its files' time to travel), as the page's own repeat does, so a letter still on its way is never called unconfirmed. When the mail server did not confirm a message, the answer is `PROVIDER_ERROR` with `send_timeout`: the message may have left, and the same request again gets the same answer without another attempt, until what became of the attempt is known. Then a repeat is answered with that: the letter left, or it failed before it was handed over and is sent. A different `id` sends it after all, once the owner has looked in Sent. That memory is the running process's: a restart forgets it. A call the client walks away from still runs to its end, and what it did is still recorded.

Give an MCP client the read token unless it needs to act on mail; keep the write token for clients you trust with the mailbox. Both are kept encrypted in the settings database and shown only once, when generated.

One message can be stored once per monitored mailbox (a forwarded copy, or a message sent to two of them). `manage_mail`, `mark_handled`, `snooze`, `record_feedback`, `read_message`, `prepare_reply`, `prepare_forward`, and `send_mail` with `replyTo` or `forward` take an optional `account`, and refuse an ambiguous id without one, naming the mailboxes, rather than acting on whichever copy was stored first. `get_mail` returns the first stored copy, lists the others under `storedFor`, and takes `account` to pick one. These tools take Message-IDs, as `list_mail` shows them, a record's key (`dedupKey`), and live handles (see [The rest of the mailbox, live](#the-rest-of-the-mailbox-live)). A sender can write a Message-ID that spells another record's key; a string that is both one record's key and another message's Message-ID is refused with `INVALID_ARGUMENT` rather than guessed, and each record is then reached by a name only it has. A string shaped like a key (an email address, `|`, the rest) only ever names a record by its key, so a key whose record is gone is not found rather than taken as a look-alike's Message-ID.

What stays with the page: its own assistant (asking a question across your mail, drafting a reply), since an MCP client is itself the model that would do that; notifications to installed copies of the page, which belong to a browser; and attaching a file from your own device, which only the page can read. Everything else a letter can be in the page, it can be through `send_mail`: an answer, a forward from any of your mailboxes with any of the original's files, Bcc, and the signature or none.

`record_feedback` records `false_positive`, `missed`, `handled`, `correct`, `spam` and `not_spam` labels for later rule and triage evaluation. Two `missed` records for one sender become an always-important rule, and two `false_positive` or `spam` records (in any mix) a never-important one; a `not_spam` for a message of that sender, recorded after them, takes its `spam` records out of the count. `not_spam` also puts back in `needs_you` a message that `spam` counted as dealt with; one marked done before stays done. `manage_mail` with `spam` or `not_spam` records the same labels as it moves the message, which is what the web view's Spam does. See [Configuration](configuration.md#your-own-rules). The `handled` label also takes the message out of the queue, but it cannot put one back: `mark_handled` is the tool for the queue.

## Attachments

`list_attachments` takes a configured account and a Message-ID or live handle, and returns MIME metadata plus a `mailsift://imap/.../attachment/{partId}` resource URI for each file. Read the resource to fetch that one file from IMAP. The web view also lists and downloads attachments from a message's detail panel. Reads use a read-only mailbox lock; attachment bytes are never stored. New triage records keep only a bounded manifest of names, MIME types, part IDs, and reported sizes.

Settings → Advanced → **MCP: largest attachment returned** (`MCP_ATTACHMENT_MAX_BYTES`) limits the decoded size of each on-demand file and defaults to 10 MiB (at most 100 MiB). This limit is separate from `MCP_LIVE_SOURCE_BYTES`, so attachment reads fetch the selected MIME part without downloading the entire message source. Filenames are treated as untrusted data and files are delivered as downloads. mailsift returns image and PDF files as-is; it does not recognize images or extract PDF text.

`scan_attachment` and the web view's **Scan attachment** button read only a bounded decoded prefix, set by Settings → Advanced → **Attachment check reads** (`MCP_ATTACHMENT_SCAN_BYTES`, default 1 MiB, at most 4 MiB). The local check looks for suspicious filename/MIME combinations and common executable, script, active-content, and container signatures. It does not unpack, execute, upload, persist, or claim to replace antivirus software.

## Spam and safety clues

The `inspect_mail_safety` tool checks a message's configured folder, mailing-list or bulk-mail headers, a From/Reply-To domain mismatch, attachment filename/MIME types, and links parsed from a bounded text body prefix. Under `senderSignals.authentication` it also repeats what the mailbox's own provider reported about SPF, DKIM and DMARC, by the same rules as the reader (`pass`, `fail`, or `none` when the provider said nothing or is not one whose header can be recognised). The web detail view offers the same check, and attachment lists show file-type cautions and a bounded scan button. Mailbox reads use a read-only lock; only the selected text body prefix is read for link parsing, and no link is opened.

Link parsing reads at most Settings → Advanced → **Link check reads** (`MCP_SAFETY_BODY_BYTES`, default 256 KiB, at most 1 MiB) from a selected text body part. It reports scheme, IP-host, punycode, userinfo, and common shortener clues while omitting URL paths and query values.

These are clues, not a spam or malware verdict. Mailing-list headers do not prove spam; sender fields can be forged. mailsift does not verify SPF, DKIM or DMARC itself (it repeats what the mailbox's own provider reported, see [Reading a message](web-view.md#reading-a-message), and a pass proves the domain, not the intent), resolve or reputation-check links, unpack attachments, or provide an antivirus verdict. It does not move, delete, flag, or otherwise change messages as part of these checks.

## Health and recovery

`health` reports the last poll heartbeat, account failures (with each failing account's last good check), LLM and decision-stage failure counts, and pending queues; `healthy` is false while a mailbox is at the alert threshold. Its `delivery` block reports the push and digest thresholds, the spam bonus, and whether self-forwards are suppressed. The container's healthcheck asks only whether a check has finished recently (see [Deployment](deployment.md#monitoring)); a healthy container does not prove that every account, LLM call, or notification sink is healthy. Use MCP `health` and `recovery_status` for those details.

The MCP recovery tools expose `recovery_status` always, and `retry_dead_letter` only to a caller holding the write token. Retrying rewinds one folder cursor so the next normal poll can fetch the message again; it does not modify the mailbox.

## Audit

Every tool and live resource call is audited by name, outcome, caller fingerprint, and (where useful) a bounded account/message/part target; rejected authentication attempts are included. A `mark_handled` row says whether the message was marked done or put back (`handled`), and a `record_feedback` row the label it was given. What the web view does is recorded the same way: its mailbox actions and each message it sends (as `send`, without recipients or text) in the mailbox-action audit, and marking done, putting off, feedback, questions, drafts and notification subscriptions as `web:*` rows in the access audit. `list_audit` returns recent rows and mailbox-action audit, and `observability` groups the access audit by tool. Credentials, message bodies, and URL query strings are never stored in the audit.
